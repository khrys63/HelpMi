Runbook d'exploitation — HelpMi

Ce document est destiné à un DevOps intervenant sans connaissance préalable de l'application. Il couvre le diagnostic et la remédiation des incidents les plus probables.

Incidents critiques — P1

Application totalement inaccessible. Intervention immédiate requise.

P1 Un ou plusieurs conteneurs sont arrêtés / en crash loop Très probable
Diagnostic rapide 
docker ps -a --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"
Repérer les conteneurs avec statut Exited ou Restarting.
Consulter les logs du conteneur en cause 
# Remplacer helpmi_backend par le nom du conteneur défaillant
docker logs helpmi_backend --tail 100
docker logs helpmi_backend --tail 100 2>&1 | grep -i "error\|exception\|fatal"
Redémarrer le service 
docker compose restart backend
# ou pour relancer tous les services
docker compose up -d
Vérifier la santé après redémarrage 
docker ps --format "table {{.Names}}\t{{.Status}}"
curl -s http://localhost:8080/actuator/health | python3 -m json.tool
Si le backend redémarre en boucle, chercher en priorité une erreur Flyway (migration SQL) ou une impossibilité de contacter MariaDB — voir incidents P2 ci-dessous.
P1 MariaDB ne démarre pas — données inaccessibles Probable
Vérifier les logs MariaDB 
docker logs helpmi_mariadb --tail 200
Chercher : InnoDB: Unable to lock ./ibdata1 (processus orphelin), Table is marked as crashed, erreurs de droits.
Cas : processus orphelin (lock file) 
docker stop helpmi_mariadb
docker rm helpmi_mariadb
docker compose up -d mariadb
Cas : corruption InnoDB — repair mode 
# Ajouter temporairement en variable d'env puis redémarrer
# Dans docker-compose.yml → environment de mariadb :
#   MARIADB_EXTRA_FLAGS: --innodb-force-recovery=1

docker compose stop mariadb
# Éditer docker-compose.yml pour ajouter la variable
docker compose up -d mariadb
docker logs helpmi_mariadb -f  # attendre "ready for connections"

# Dump immédiat avant tout
docker exec helpmi_mariadb sh -c \
  "mysqldump -u root -p\$MYSQL_ROOT_PASSWORD helpmi" > backup_recovery.sql

# Retirer le flag innodb-force-recovery et redémarrer normalement
P1 Disque plein — conteneurs figés ou en erreur d'écriture Probable
Identifier la consommation 
df -h
docker system df
du -sh /var/lib/docker/volumes/*/
Nettoyer les ressources Docker inutilisées 
# Images/conteneurs/réseaux non utilisés (SANS supprimer les volumes)
docker system prune -f

# Logs de conteneurs (souvent très volumineux)
truncate -s 0 $(docker inspect --format='{{.LogPath}}' helpmi_backend)
truncate -s 0 $(docker inspect --format='{{.LogPath}}' helpmi_mariadb)
Limiter la taille des logs (prévention) 
# À ajouter dans docker-compose.yml sur chaque service concerné :
#   logging:
#     options:
#       max-size: "50m"
#       max-file: "3"

Incidents majeurs — P2

Une fonctionnalité clé est dégradée. Les utilisateurs sont impactés.

P2 Backend refuse de démarrer — erreur Flyway (migration SQL) Très probable après un déploiement

Flyway bloque si une migration échoue ou si le checksum d'un fichier existant a changé.

Identifier l'erreur exacte 
docker logs helpmi_backend 2>&1 | grep -A 5 "FlywayException\|Migration"
Messages courants :
  • Validate failed: Migration checksum mismatch → le fichier SQL a été modifié après application
  • Migration V14__ failed → erreur SQL dans la nouvelle migration
  • Table 'flyway_schema_history' doesn't exist → base vierge, premier démarrage
Cas checksum mismatch — repair 
# Se connecter à la base
docker exec -it helpmi_mariadb mysql -u helpmi -p helpmi

-- Voir l'état des migrations
SELECT version, description, success, checksum FROM flyway_schema_history ORDER BY installed_rank DESC LIMIT 10;

-- Supprimer l'entrée problématique (Flyway la réappliquera)
-- ATTENTION : ne faire que sur une migration ayant échoué (success=0)
DELETE FROM flyway_schema_history WHERE success = 0;
Relancer le backend 
docker compose restart backend
docker logs helpmi_backend -f
Ne jamais modifier un fichier V*.sql déjà appliqué en production. Toute correction doit passer par un nouveau fichier V(n+1)__fix_xxx.sql.
P2 Authentification impossible — Keycloak KO Probable
Vérifier que Keycloak répond 
curl -s http://auth.localhost/realms/helpmi/.well-known/openid-configuration | python3 -m json.tool | head -10
# Doit retourner un JSON avec "issuer", "token_endpoint"...
Redémarrer Keycloak 
docker compose restart keycloak
# Attendre ~30s le démarrage complet
docker logs helpmi_keycloak -f | grep -i "started\|error"
Vérifier que le realm est bien importé 
# Accéder à l'admin Keycloak : http://auth.localhost/admin
# Login : valeurs KEYCLOAK_ADMIN / KEYCLOAK_ADMIN_PASSWORD du .env
# Vérifier que le realm "helpmi" existe dans la liste

# Si le realm manque : forcer la réimportation
docker compose down keycloak
docker compose up -d keycloak
Le realm est réimporté depuis keycloak/realm-export.json au démarrage. Si ce fichier est absent ou corrompu, l'import échoue silencieusement.
Tester la récupération d'un token (smoke test) 
curl -s -X POST http://auth.localhost/realms/helpmi/protocol/openid-connect/token \
  -d "client_id=helpmi-frontend" \
  -d "grant_type=password" \
  -d "username=admin" \
  -d "password=admin123" \
  | python3 -m json.tool | grep "access_token\|error"
P2 Upload de fichiers impossible — MinIO KO Probable
Vérifier la santé MinIO 
curl -sf http://localhost:9000/minio/health/live && echo "OK" || echo "KO"
Redémarrer MinIO 
docker compose restart minio
docker logs helpmi_minio --tail 50
Vérifier que le bucket existe 
# En dev, accéder à la console : http://localhost:9001
# Login : MINIO_ROOT_USER / MINIO_ROOT_PASSWORD du .env
# Le bucket "helpmi" doit exister

# En CLI avec le client mc (si installé sur la machine)
docker run --rm --network host \
  -e MC_HOST_local="http://\${MINIO_ROOT_USER}:\${MINIO_ROOT_PASSWORD}@localhost:9000" \
  minio/mc ls local/
Recréer le bucket si absent 
docker exec helpmi_minio sh -c \
  "mc alias set local http://localhost:9000 \$MINIO_ROOT_USER \$MINIO_ROOT_PASSWORD && \
   mc mb local/helpmi || true"
Le bucket n'est pas créé automatiquement au premier démarrage. Le backend le crée lui-même au démarrage via le SDK S3 — vérifier les logs backend si le bucket est manquant.
P2 Frontend inaccessible (page blanche / 502) Probable
Vérifier le conteneur Nginx 
docker logs helpmi_frontend --tail 50
curl -I http://localhost:3000
Cas 502 sur /api/* — backend non joignable 
# Le 502 vient du proxy Nginx → backend
# Vérifier que le backend tourne
docker ps | grep helpmi_backend
curl -s http://localhost:8080/actuator/health
Redémarrer le frontend 
docker compose restart frontend

Incidents modérés — P3

Fonctionnalité partielle dégradée. Contournement possible.

P3 Backend lent / timeouts sur l'API Probable
Vérifier la charge du conteneur 
docker stats --no-stream helpmi_backend helpmi_mariadb
Chercher des requêtes SQL lentes 
docker exec -it helpmi_mariadb mysql -u root -p helpmi -e \
  "SHOW PROCESSLIST;"

# Voir les slow queries (si activé)
docker exec helpmi_mariadb mysql -u root -p helpmi -e \
  "SHOW VARIABLES LIKE 'slow_query%';"
Vérifier les connexions actives 
docker exec helpmi_mariadb mysql -u root -p helpmi -e \
  "SELECT count(*) as connexions FROM information_schema.PROCESSLIST;"
Redémarrer le backend pour libérer le pool 
docker compose restart backend
P3 Erreurs CORS — API bloquée par le navigateur Occasionnel après changement d'URL

Symptôme : erreur "Access-Control-Allow-Origin" dans la console du navigateur.

Vérifier la variable CORS dans .env 
# Dans .env :
APP_CORS_ALLOWED_ORIGINS=http://localhost:3000   # ← doit matcher l'URL du navigateur
Corriger et redémarrer le backend 
# Éditer .env, puis :
docker compose up -d --force-recreate backend
P3 Token JWT invalide / 401 en boucle Occasionnel
Vérifier que l'issuer URI est cohérent 
# La variable APP_KEYCLOAK_ISSUER_URI dans .env doit correspondre
# à ce que Keycloak retourne dans son discovery document :
curl -s http://auth.localhost/realms/helpmi/.well-known/openid-configuration | \
  python3 -c "import sys,json; d=json.load(sys.stdin); print(d['issuer'])"

# Doit correspondre à APP_KEYCLOAK_ISSUER_URI dans .env
Si l'URL diffère (docker interne vs external) 
# En prod, Keycloak est souvent accessible via 2 URLs :
# - interne (conteneur → conteneur) : http://keycloak:8080/realms/helpmi
# - externe (navigateur → hôte)     : http://host:8180/realms/helpmi
# APP_KEYCLOAK_ISSUER_URI doit pointer vers l'URL EXTERNE (celle du navigateur)

Incidents mineurs — P4

Impact limité, pas de perte de données, résolution planifiable.

P4 Un utilisateur ne peut pas se connecter Occasionnel
Vérifier dans Keycloak admin 
# http://auth.localhost/admin → Realm helpmi → Users
# Chercher l'utilisateur → vérifier : "Enabled", "Email Verified", pas de lock
Réinitialiser le mot de passe via l'admin Keycloak 
# Users → l'utilisateur → Credentials → Reset password
Vérifier le rôle dans la base applicative 
docker exec -it helpmi_mariadb mysql -u helpmi -p helpmi -e \
  "SELECT id, email, role, active, organization_id FROM users WHERE email='user@example.com';"
P4 Un utilisateur voit la page "en attente d'affectation" Nominal — workflow attendu

Ce n'est pas un bug : tout utilisateur sans organisation est bloqué sur cette page par design. Un administrateur doit lui affecter une organisation depuis Admin → Utilisateurs.

En cas d'urgence, affectation directe en base :

-- Trouver l'ID de l'organisation cible
SELECT id, name FROM organizations WHERE active = 1;

-- Affecter l'utilisateur
UPDATE users SET organization_id = 'UUID-DE-LORG' WHERE email = 'user@example.com';

Commandes routinières

État général

# Tous les conteneurs et leur état
docker ps -a --format "table {{.Names}}\t{{.Status}}"

# Consommation ressources en temps réel
docker stats

Logs

# Suivre les logs en direct
docker logs -f helpmi_backend

docker logs -f helpmi_keycloak

# 50 dernières lignes d'erreur
docker logs helpmi_backend 2>&1 | grep -i error | tail -50

Base de données

# Connexion interactive
docker exec -it helpmi_mariadb mysql -u helpmi -p helpmi

# Compter les tickets
docker exec helpmi_mariadb mysql -u helpmi -p helpmi -e \
  "SELECT status, COUNT(*) FROM tickets GROUP BY status;"

docker exec helpmi_mariadb mysql -u helpmi -p helpmi -e \
  "SELECT version, description, success FROM flyway_schema_history ORDER BY installed_rank;"

MinIO

# Taille occupée par le bucket
docker exec helpmi_minio du -sh /data/helpmi/ 2>/dev/null || \
  docker exec helpmi_minio du -sh /data/

# Santé
curl -sf http://localhost:9000/minio/health/live && echo OK

Sauvegarde & Restauration

Sauvegarde MariaDB

# Dump complet (base helpmi) avec timestamp
docker exec helpmi_mariadb sh -c \
  'mysqldump -u root -p$MYSQL_ROOT_PASSWORD --single-transaction helpmi' \
  > backup_helpmi_$(date +%Y%m%d_%H%M%S).sql

# Vérifier le dump
head -20 backup_helpmi_*.sql   # doit commencer par un commentaire mysqldump

Restauration MariaDB

Destructif. Cette opération écrase la base existante. Faire un dump avant.
# Restaurer depuis un fichier de dump
docker exec -i helpmi_mariadb sh -c \
  'mysql -u root -p$MYSQL_ROOT_PASSWORD helpmi' \
  < backup_helpmi_20260101_120000.sql

Sauvegarde MinIO (pièces jointes)

# Copier le volume sur l'hôte
docker run --rm \
  -v minio_data:/source:ro \
  -v $(pwd)/backup_minio:/backup \
  alpine tar czf /backup/minio_$(date +%Y%m%d).tar.gz -C /source .

Restauration MinIO

docker run --rm \
  -v minio_data:/target \
  -v $(pwd)/backup_minio:/backup \
  alpine tar xzf /backup/minio_20260101.tar.gz -C /target

Reset environnement de développement

Développement uniquement. Ces commandes suppriment toutes les données.
# Reset complet (supprime conteneurs + volumes)
docker compose down -v

# Redémarrage propre (réimporte le realm Keycloak, rejoue les migrations Flyway)
docker compose up -d

# Vérifier que tout est healthy
docker ps --format "table {{.Names}}\t{{.Status}}"

Pour le mode dev avec phpMyAdmin :

docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d

Redéploiement (mise à jour applicative)

Sauvegarde préalable obligatoire 
docker exec helpmi_mariadb sh -c \
  'mysqldump -u root -p$MYSQL_ROOT_PASSWORD --single-transaction helpmi' \
  > backup_before_deploy_$(date +%Y%m%d_%H%M%S).sql
Mettre à jour les sources 
git pull origin main
Reconstruire et redémarrer 
# Rebuild des images backend et frontend
docker compose build --no-cache backend frontend

# Redémarrer sans toucher aux volumes
docker compose up -d --force-recreate backend frontend
Vérifier les migrations Flyway 
docker logs helpmi_backend 2>&1 | grep -E "Flyway|migration|Migrating"
# Chercher "Successfully applied X migrations"
Smoke test 
curl -s http://localhost:8080/actuator/health
curl -I http://localhost:3000

Traefik — Opérations

P2 Un service n'est pas joignable via son sous-domaine Probable
Ouvrir le dashboard Traefik 
http://traefik.localhost    # ou http://localhost:8090/dashboard/
Vérifier que le router du service apparaît dans HTTP → Routers avec statut Enabled.
Vérifier que le conteneur tourne et a les bons labels 
docker inspect helpmi_frontend | grep -A 20 '"Labels"'
Les labels traefik.enable=true et traefik.http.routers.* doivent être présents.
Vérifier que le conteneur est sur le réseau helpmi_proxy 
docker inspect helpmi_frontend | grep -A 5 '"Networks"'
# helpmi_proxy doit apparaître
Consulter les logs Traefik 
docker logs helpmi_traefik --tail 50
docker logs helpmi_traefik --tail 100 2>&1 | grep -i "error\|warn"
Forcer la redécouverte des conteneurs 
docker compose restart traefik
P3 Keycloak — erreur "invalid issuer" / tokens rejetés après changement de domaine Après modification de TRAEFIK_DOMAIN

L'issuer dans les tokens JWT est baked au moment de leur émission. Si TRAEFIK_DOMAIN change, les anciens tokens sont invalides et les nouveaux ne correspondent plus si le backend n'est pas redémarré.

Vérifier la cohérence issuer / backend 
# Issuer que Keycloak encode dans les tokens :
curl -s http://auth.localhost/realms/helpmi | python3 -c "import sys,json; print(json.load(sys.stdin)['issuer'])"

# Issuer que le backend attend (variable APP_KEYCLOAK_ISSUER_URI) :
docker inspect helpmi_backend | grep KEYCLOAK_ISSUER
Les deux valeurs doivent être identiques.
Si elles diffèrent — recréer backend et keycloak 
# Mettre à jour TRAEFIK_DOMAIN dans .env, puis :
docker compose up -d --force-recreate keycloak backend
# Attendre ~30s, tester un login
Le frontend doit aussi être rebuild car VITE_KEYCLOAK_URL est baked dans l'image Nginx au moment du docker compose build.

Migration HTTPS (production)

Prérequis : nom de domaine pointé sur le serveur, port 443 ouvert.

1. Configurer le domaine dans .env

TRAEFIK_DOMAIN=helpmi.example.com
ACME_EMAIL=ops@helpmi.example.com
APP_CORS_ALLOWED_ORIGINS=https://app.helpmi.example.com

2. Créer le fichier ACME vide (requis par Traefik)

mkdir -p traefik/letsencrypt
touch traefik/letsencrypt/acme.json
chmod 600 traefik/letsencrypt/acme.json

3. Décommenter les blocs HTTPS dans docker-compose.yml

Chercher tous les commentaires # HTTPS et décommenter les lignes correspondantes :

  • Entrypoints websecure et redirection HTTP→HTTPS dans Traefik
  • Port 443:443
  • Volume ./traefik/letsencrypt:/letsencrypt
  • Labels tls.certresolver=letsencrypt sur chaque router

4. Rebuild frontend + redémarrage

# Le VITE_KEYCLOAK_URL doit être rebuild avec la nouvelle valeur
docker compose build --no-cache frontend
docker compose up -d

5. Vérifier l'obtention du certificat

docker logs helpmi_traefik -f | grep -i "acme\|certificate\|error"
# Attendre "Certificates obtained successfully"

# Test SSL
curl -sv https://app.helpmi.example.com 2>&1 | grep -i "SSL\|certificate\|issuer"
Let's Encrypt impose une limite de 5 certificats par domaine par semaine. En test, utiliser le staging ACME : ajouter --certificatesresolvers.letsencrypt.acme.caserver=https://acme-staging-v02.api.letsencrypt.org/directory dans la commande Traefik.
